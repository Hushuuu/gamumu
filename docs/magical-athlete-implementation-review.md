# Magical Athlete：實作評估與階段目標

評估日期：2026-10-10。依據目前專案程式碼與 [原始規則整理](./magical-athlete-plan.md)。本文件只提出實作規劃，尚未新增遊戲功能。

## 1. 評估結論

**適合加入 GAMUMU，現有多人房間架構可以承接；但原始文件是玩法資料，還不足以直接作為開發規格。**

選秀、秘密派出選手、擲骰、四場累計得分，都能沿用目前的遊戲模組介面。主要成本在「可暫停、可恢復的能力結算引擎」，尤其是非當前玩家的選擇、同時到達、重擲、複製能力，以及雙選手回合。若直接在擲骰處堆疊 36 個角色判斷，後續非常容易出現結算順序錯誤與重連無法繼續。

建議順序：先補齊規則與數值 → 建立結算核心 → 完成 3–6 人單選手模式 → 補齊高互動角色 → 加入 2 人及 3 人雙選手模式 → 正式開放。內部測試可先使用受限角色池，但應明確標示，不能稱為完整基本版。

| 面向 | 評估 | 實作意義 |
| --- | --- | --- |
| 現有系統接入 | 難度低至中 | 已有遊戲註冊表、私密事件、alarm、結果元件 |
| 一般競賽流程 | 難度中 | 需要選秀、秘密選角、四場狀態機與分數帳本 |
| 36 名選手互動 | 難度高 | 核心必須區分事件類型、觸發時點與選擇權 |
| 雙選手變體 | 難度高 | 玩家與選手不能共用同一個 ID／回合概念 |
| 手機呈現 | 難度中 | 要看懂能力連鎖，同時維持清楚的操作入口 |
| 現有資料完整度 | 尚不足 | 缺正式賽道、獎分與部分互動裁定 |

| Egg 抽牌 | 抽三張後選能力 | 未選卡與選中卡的去向、牌堆不足、剩餘牌堆跨場保留方式 |
| Twin／複製鏈 | 能複製能力 | 複製已變身冠軍時取原能力還是本場實際能力；遞迴複製及空目標的裁定 |

本次核對發現：原文件把 Sisyphus 的 6 點寫成「不執行該次移動」，但所引用的 [RulesPal 英文頁面](https://www.rulespal.com/magical-athlete/rulebook) 另寫傳送後仍保有主要移動，並提到有分數時可繼續扣分。這會改變競賽與計分，應核對採用版本後再實作。

來源中的 [BoardGame Archive 整理](https://boardgamearchive.com/how-to-play/how-to-play-magical-athlete/) 自稱依 2026-08-17 更新，並連到 [規則檔案頁](https://boardgamegeek.com/filepage/307679/how-to-play-magical-athlete)。本次檔案頁存取回傳 403，未取得該 PDF；因此不能宣稱已驗證最新版全部裁定。官方 [CMYK 商品頁](https://www.cmyk.games/products/magical-athlete) 可確認遊戲身分與 2–6 人範圍，但不能替代完整規則。

### 2.2 必須形成測試案例的互動問題

| 問題 | 為什麼目前描述不夠 | 建議處理 |
| --- | --- | --- |
| 起始擲骰平手 | 「下一高點」未完整描述多層平手／無唯一點數 | 固定 roll-off 演算法並測試多種結果；由伺服器擲骰 |
| 下一場最落後者平手 | 未指定同格時的先手 | 待核對；若無正式裁定，明訂候選玩家間擲骰的數位規則 |
| 同時跨終點 | 跟隨移動可能同時完賽 | 先訂名次裁定，不能依 WebSocket 到達順序分冠亞軍 |
| 第二名成立時的待處理效果 | 「立即結束」與效果連鎖可能交錯 | 在明確完賽檢查點停止尚未執行的競賽效果；已記帳分數保留 |
| 強制移動的多人次序 | Cheerleader、Party Animal 涉及多名選手 | 決定同時移動或逐名結算，保存事件前狀態，避免名單迴圈改變目標 |
| Move／Warp／放置 | 傳送不算移動，但仍可能形成停留 | 分開事件種類；不要把傳送理解為完全不觸發賽道或停留能力 |
| Huge Baby 位置修正 | 會改變到達格與同格狀態 | 明訂替代位置的時點、多人同時到達與複製衝突；不製造假的超越事件 |
| 主移動距離修正 | 替代距離、倍增、加減可能同時存在 | 先固定運算順序與取樣時點；對負值／零值明訂行為 |
| 重擲選擇 | Magician 與 Dicemonger 可重疊 | 分別記錄能力使用次數與骰值接受狀態；棄用骰值不觸發點數能力，重擲行為另記錄 |
| 重新絆倒 | 已絆倒、恢復回合再次被絆倒 | 用主移動跳過義務與事件時序表示，不以回合結尾一律清除布林值 |
| Duelist 重複決鬥 | 同格時可多次，且不能中斷動作 | 定義可宣告的安全時點與放棄後再開窗口條件；不能任意加「一回合一次」 |
| Copycat 更新 | 領先者可在連鎖中改變或有多人 | 明訂每次查詢／快照更新時點、選擇維持條件與自我複製處理 |
| 雙選手優先權 | 規則以玩家排序，玩家控制兩選手 | 確認同玩家兩能力先後、額外回合及 Skipper 指向哪一層回合 |
| 少於兩名可完賽者 | 淘汰或離開使比賽無法正常結束 | 區分官方淘汰與玩家退房；訂零存活、一存活、有冠軍無亞軍的收尾 |

最需要先交叉驗證的組合：Suckerfish × Stickler／Romantic、Huge Baby × Party Animal／Copycat、Magician × Dicemonger × Scoocher、Genius × Skipper，以及 Mastermind 同時取得兩名次的情況。

## 4. 應調整或明訂的線上行為

這些是為現有房間架構提出的數位版政策，應放入遊戲內規則說明。倒數數值是建議預設，尚未實作。

### 4.1 玩家、選手與固定座位

- `playerId` 表示操作者；`racerInstanceId` 表示本場的選手；角色卡 ID 表示能力來源。不同選手即使共用能力，也不能合併身分。
- 遊戲開始時保存固定 `seatOrder` 與玩家名稱快照。順時針按座位判定，不能用在線名單或當下分數排序。
- 本場被淘汰不等於退房，玩家下場仍可派出其他選手；冠軍完賽後仍留在房間觀看。
- 沿用開始前全員在線且 Ready 的條件。房間可容納 12 人，但遊戲只接受模式允許的人數；第一版不新增旁觀者容量。
- 四場為「同一局」，不能每場使用 `prepare_next_game` 或清空準備狀態。

### 4.2 選秀與秘密派出

選秀結果原本就是公開資訊，因此已選隊伍可以公開；真正需要隱藏的是「本場尚未揭露的派出選擇」、Egg 私密候選，以及尚未公開的牌堆內容。

建議派出後即鎖定，公開快照只顯示是否已提交；全員提交或逾時補齊後，伺服器一次公開。這是要明訂的數位操作政策，避免最後提交者因封包先後看到他人的選手。

`toView()` 只輸出公開資訊；`privateState()` 給本人候選、選擇與可用操作，可採用 `pushPrivateState: true`。重連驗證時，房間已有私密重送流程。兩種資料都帶 `stateVersion`，前端收到不同版本時先等待配對，避免短暫顯示過期操作。

### 4.3 限時與自動處理

| 等待項目 | 建議預設 | 逾時行為 |
| --- | --- | --- |
| 選秀 | 30 秒 | 從仍合法的候選中伺服器隨機選一張並記錄 |
| 每場秘密派出 | 30 秒 | 從尚未使用的選手隨機補足所需數量 |
| 當前選手操作 | 20 秒 | 執行正常擲骰；已絆倒依規則跳過主要移動 |
| 可選能力／是否重擲 | 10 秒 | 放棄可選能力、接受當前骰值 |
| 強制選擇目標／能力 | 15 秒 | 從合法候選中選擇；無合法目標依能力規格收尾 |
| 場間結果 | 5 秒 | 自動進下一場準備；結果保留可查 |

只有合法選項才可自動採用；自動操作與隨機結果須保存。主移動與子選擇應有不同 deadline，子選擇暫停主回合倒數，否則等待他人能力會吃掉自己的操作時間。

模組以 `nextAlarmAt()` 回傳最近的待處理期限，`handleAlarm()` 推進；房間會與閒置到期時間取最早值。收到操作也要先檢查 `now >= deadline`，確保 alarm 延後到達時不接受過期答案。

### 4.4 斷線、退房與房主中止

現況：WebSocket 關閉只更新 `online`，**不會**呼叫 `onPlayerLeave()`；明確退房則先從 `room.players` 移除玩家，再呼叫模組離開處理。

因此建議：

1. 暫時斷線保留角色與座位，依既有 deadline 自動操作；重連後從快照與 pending choice 繼續，不另開一局。
2. 明確退房的第一版政策：結束整局且不結算本局分數，標示 `endReason: player-left`。原因是退出選秀、移除被複製對象、雙選手退場與場間人數變更，會額外增加一套非原規則。
3. 若日後要支援剩餘玩家繼續，應另外規劃退房座位、剩餘卡牌、先手、分數與能力撤除政策，不能直接套用 M.O.U.T.H. 淘汰。
4. 房主「提前結束本局」沿用 `abort_game`，不改成發放目前部分獎分。房主暫時離線的行為維持現制；明確離開會由房間轉移房主。

退房回呼讀不到已移除的玩家，故本局座位與帳本必須保存於遊戲狀態。若採下節「局末一次入帳」，退房結束只需保持本局未入帳，避免呼叫模組不能取得的房間私有方法。

### 4.5 本局得分與房間累計分數

目前 `PlayerView.score` 是跨遊戲累積分數，**不能直接拿它判斷本局勝者**。

建議遊戲內另存 `matchPoints[playerId]` 與來源帳本：場次冠亞軍、星星、角色加分／扣分。競賽中只更新本局帳本，第四場完成時一次把各玩家本局得分加入房間累計分數，並保存 `scoresCommitted`／結算 ID，避免重複入帳。

優點是房主中止、退房提前結束都可不結算；也不需要沿用拉密特有的局末 `settle_scores` 例外。目前房間在 `finished` 狀態只放行拉密該操作，新遊戲若採房主確認後入帳，必須明確擴充房間層，不能只新增模組 action。

同分本局勝者用 `winnerIds`。結果元件顯示四場獎分與能力／賽道分數，再呈現房間累積分數；本局排名應按 `matchPoints` 排序。Sisyphus 扣分不得扣到玩家過往遊戲的累計分數。

### 4.6 動畫與判定

伺服器決定骰值、位置、觸發次序與名次；前端只能送出意圖，不接受前端指定骰值或移動後座標。

建議公開狀態包含有限長度的結算紀錄，每則有遞增序號及前後位置。前端逐則播放移動、絆倒、淘汰、得分；狀態快照仍是權威。玩家可略過動畫，重連可直接顯示最新狀態，動畫結束不是推進回合的必要條件。

`useGameRoom()` 目前只保留最新一筆 `gameEvent`，因此不可把關鍵紀錄只放在瞬時事件。房間的 room audience 事件還會排除發起者，操作回應不宜作為所有客戶端共用的唯一動畫來源。

手機優先顯示當前操作者、選手、可選能力與倒數；賽道上的同格選手以堆疊／展開查看，提供文字結算紀錄與能力說明。雙選手模式用明確選手切換，不讓使用者混淆正在操作哪名選手。

## 5. 結算引擎設計建議

### 5.1 狀態機

建議遊戲內階段為：

```text
draft → race-select → pre-race → racing → race-results
                                      ↑          │
                                      └─ 下場準備 ┘
第四場結束 → finished
```

場間結果後應回到 `race-select`，不是直接開始下一名選手的回合。房間外層仍只有 `waiting / playing / finished`；選秀與四場競賽皆屬於 `playing`。

`racing` 裡再區分回合開始、主要移動前、擲骰／重擲、接受骰值、擲骰能力、主要移動、連鎖結算、回合結束；任何需要玩家選擇的節點都可停在 `pendingChoice`。

### 5.2 最少需要保存的狀態

| 類別 | 建議內容 |
| --- | --- |
| 版本與模式 | `schemaVersion`、`rulesVersion`、模式、賽道排程、限制角色池 |
| 選秀 | 剩餘牌堆、公開候選、完整選秀次序、進度、每人隊伍 |
| 玩家 | 固定座位、名稱快照、派出狀態、本局分數與帳本 |
| 選手 | instance ID、擁有者、卡牌 ID、能力來源、位置、絆倒、完賽／淘汰狀態 |
| 當前場次 | 場號、賽道、先手、名次、淘汰順序、場初分數 |
| 回合 | `turnId`、操作者、行動選手、回合起始位置、已用時點能力、額外回合／改序資訊 |
| 骰子 | 最近骰子 ID、用途、歷次擲骰、接受值、各來源重擲次數 |
| 續行 | 可序列化效果佇列／結算堆疊、進行中事件、待選對象、期限、循環偵測資料 |
| 紀錄／結束 | 序號化公開紀錄、四場結果、`winnerIds`、結算旗標、提前結束原因 |

所有等待狀態必須是可序列化的資料。不能把函式、閉包、Vue 狀態或尚未完成的 Promise 放在持久化續行中。現有 `GameModule.handleAction()` 是同步介面，應在無需等待時結算到下一個選擇／完成節點，再回傳保存，而不是在裡面等待玩家封包。

### 5.3 事件與能力

至少區分：`MainMove`、能力 `Move`、`Warp`、非移動 `Placement`、`RollAccepted`、`RerollUsed`、`Stopped`、`Passed`、`AbilityApplied`、`TurnEnded`、`Finished`、`Eliminated`。

每次位移記錄起點、終點、原因、參與選手與是否為同步批次。依資料判定超越與停留，不從動畫途中經過的格子推導。能力處理器應分成條件檢查、產生效果、選項與續行，並記錄使用者及能力來源，方便複製能力及 Scoocher 追蹤。

同時觸發先依原文件的賽道／當前玩家／其他玩家座位順序排序；同一玩家多選手的順序另需裁定。效果产生新事件時，使用明確的結算堆疊／事件 frame 定義新連鎖先處理或延後，不要用一個普通 FIFO 佇列就假設所有時序都正確。

骰值接受前只處理重擲選擇；接受後才觸發 1／6 點相關能力。Scoocher 監聽重擲行為、實際能力生效等事件，不以「每次能力函式被呼叫」計數。

### 5.4 無限循環與執行量

原規則允許有限連鎖持續，因此「每回合最多 100 次效果」只能當執行保護，不能直接當正式遊戲裁定。建議使用與未來轉移相關的狀態簽章及事件鏈偵測循環；分數、可用次數、待選擇等會影響後續的資料也必須納入。

另設每次請求的處理步數預算，長連鎖保存 continuation 後用 alarm 續行，不任意停止合法效果。循環偵測命中時，按已確認的「完整一次循環」政策收尾並留下說明；無法判定的引擎錯誤保留診斷與中止出口，不能靜默丟棄效果。

### 5.5 操作驗證與續行

採用 `draft_pick`、`select_racers`、`roll_main`、`resolve_choice` 等少量語意明確的操作。Worker 驗證 phase、操作者、選手所有權、未使用卡牌、合法目標、期限及選擇 ID。

`resolve_choice` 帶 `choiceId`；選秀／回合操作帶對應進度 ID，必要時加 `actionId` 去重。一般選角不要用全域版本要求全員相同，否則其他玩家合法提交造成版本更新，會錯誤拒絕自己的秘密選角；應按本場選擇與本人提交狀態驗證。

重連後使用同一 `choiceId` 續行，不能重新抽牌或重擲骰。測試用可注入亂數來源，正式骰值只由伺服器產生並保存結果。

## 6. 角色實作分組

以下是工程風險分組，並非玩法強弱排序；36 名角色均列入。分組可作為迭代順序，正式完整版仍須覆蓋全部。

| 分組 | 角色 | 需要先具備的核心 |
| --- | --- | --- |
| 距離與條件 | Alchemist、Blimp、Coach、Gunk、Hare、Legs、Lovable Loser、Rocket Scientist | 骰值與距離分離、時點取樣、可選操作、加減與絆倒 |

## 7. 驗證與驗收要求

專案目前 `package.json` 沒有 test script。新遊戲需要加入能執行規則測試的最小工具與指令，不必先建全專案的大型測試框架。

必要測試包含：

- 3–6 人兩輪蛇形選秀、2 人 ABBAABBA 與反轉、3 人四輪輪換；卡牌數量守恆與無重複派出。
- Move／Warp／Placement／Move 0、起點、終點、超越、精確完賽、絆倒恢復及再次絆倒。
- 棄用骰值不觸發骰點能力；重擲本身可觸發相關效果；多來源重擲與前置能力不重複執行。
- 第 2.2 節的高互動組合、同步到達、兩選手優先序、複製來源退出與循環。
- 第二名立即結束、無亞軍、Mastermind 雙名次、同分多勝者、四場與局末只入帳一次。
- 節點保存後重新載入能繼續同一選擇；過期操作、多分頁重複點擊、他人操作、錯選手 ID 被拒絕。
- 公開 snapshot／紀錄不洩漏秘密派出、Egg 候選或牌堆；私密事件只發給本人。
- 暫時斷線、明確退房、房主中止、alarm 延遲、長連鎖續行與房間過期的收尾。

多客戶端煙霧測試至少涵蓋 3／6 人單選手、2 人雙選手及 3 人雙選手完整四場。前端驗收包含手機窄螢幕、同格多選手、非當前玩家的待選能力、略過動畫及重連恢復。

程式實作階段需要通過 `npm run build` 與 `npm run worker:check`。本次只新增評估文件，未執行程式建置，亦未修改原始規則文件。

## 8. 階段目標與完成條件

### 階段 0：固定資料與裁定

**目標：把玩法整理轉成可以測試的規則規格。**

交付：兩面賽道資料、四場獎分、36 名能力版本表、缺口與互動裁定清單、退房／逾時／計分政策。

完成條件：不再有以「依實物」「依轉角外觀」代替程式資料的項目；Sisyphus、同步完賽、雙選手回合與複製鏈都有採用版本或明示數位裁定。未解決裁定須對應禁用範圍，不能默默採用猜測。

### 階段 1：模組接入與結算核心

**目標：能在現有房間啟動並保存新遊戲。**

交付：共用型別／validator、兩側註冊、基本狀態機、選秀與秘密派出、移動事件、pending choice、alarm、基本結果頁、可注入亂數的測試入口。遊戲目錄保持未公開。

完成條件：3–6 人測試角色可跑完四場；重連不重擲、不重新選牌；錯誤／過期操作被拒絕；本局與跨局分數分開；中止與退房不結算。

### 階段 2：單選手內部可玩版

**目標：驗證選秀策略、能力互動與手機體驗。**

交付：分組前兩組角色及視測介面，逐步擴充角色池、兩面賽道、結算紀錄與動畫、測試 bot。限制角色池時內測先限定 3–4 人，池至少 16 名、排除需要額外抽牌的未完成角色，確保四人選秀有足量卡牌。

完成條件：限定配置能完整遊玩四場，公開顯示目前角色池與限制；逾時與非當前玩家選擇不會卡局；有可讀的效果順序，且動畫不影響裁決。

### 階段 3：36 名角色與標準 3–6 人模式

**目標：完成標準版能力與高互動裁定。**

交付：其餘角色、同步移動、重擲與行動順序、複製能力、循環偵測與續行、完整角色池、四場紀錄與多勝者結果。

完成條件：36 名能力均有至少一個正向與必要的例外測試，高風險組合通過；3／6 人多端完整四場通過；私密與持久化測試通過。此階段可開放標示「3–6 人標準模式」的封測。

### 階段 4：雙選手模式

**目標：完成原文件的 2 人與 3 人雙選手變體。**

交付：模式設定、不同選秀次序、每人八張卡、每場兩選手、玩家回合／選手行動分層、場次先手判定與雙選手 UI。

完成條件：2 人首回合與後續雙行動按已確認裁定運作；3 人雙選手六名競賽完成；同玩家另一名選手符合「其他選手」；Skipper／Genius／多能力優先序、其中一名完賽或淘汰都不破壞回合。模式人數從前端到 Worker 一致驗證。

### 階段 5：正式開放

**目標：在遊戲目錄提供清楚、穩定的完整模式。**

交付：完整規則說明、數位版差異、資產與手機版面、結果明細、README／開發文件更新；必要的長連鎖與失敗診斷。

完成條件：所有模式多端與重連驗收通過，建置與 Worker 型別檢查通過，沒有已知會阻塞比賽的裁定缺口，再啟用遊戲目錄。回歸確認現有遊戲的啟動、分數、abort 與下一局流程。

各階段先以完成條件估工，不直接用「每個角色一樣的工時」估算。階段 0 的裁定結果及階段 1 的同步／續行原型，會決定後續工作量。
